# GD Roblox Kickoff — идея → документы → проверяемый MVP scope

## Назначение и происхождение

Это Roblox-расширение подхода VKSpaz/gd-doc-kickoff. Исходный навык делает интервью **по одной фиче** и не создаёт концепт/feature index. Данный навык сначала оформляет идею целой игры, затем сужает до одной основной механики и использует методику feature-интервью из оригинала. Оригинальный навык и его материалы находятся по адресу https://github.com/VKSpaz/gd-doc-kickoff. Инсталлятор может загрузить исходные материалы в references/upstream/ как справочные тексты; их отсутствие не блокирует этот навык.

## Когда включать

- Пользователь голосом или текстом произносит: «у меня идея Roblox-игры», «запиши концепт», «сделай фича-индекс», «сделаем MVP», «начнём новую игру в Roblox».
- Можно вызвать явно: $gd-roblox-kickoff.
- Не включай для одной технической правки, проверки скрипта или уже документированной механики — это область roblox-mvp-builder.
- Если пользователь одной фразой просит и оформить идею, и сделать прототип, сначала **закрой документационный этап** и передай управление следующему навыку в рамках разрешённого сеанса; не выдавай текст за работающий прототип.
- Работа только с дизайн-документами. Не писать Luau, не устанавливать программы, не создавать или менять объекты Studio, не публиковать игру.

## Режим общения: удобно диктовать голосом

Говори по-русски, коротко и обычными словами. Не заставляй пользователя диктовать названия переменных, точные пути, класс/RemoteEvent или таблицы.

1. В первой реплике перескажи услышанную идею в 2–4 предложениях. Если суть понятна, не останавливай процесс ради повторного описания.
2. За раунд спроси максимум **1–3 наиболее важных** вопроса. Если пользователь предпочитает голос, держи вопросы короткими.
3. Разделяй утверждения пользователя, допущения и твои предложения. Факты без источника не выдумывай.
4. Для неопределённой механики предложи максимум два варианта с различием, а не большой список.
5. Если ответов достаточно для минимального прототипа, прекращай интервью и создавай документы. Не вынуждай проводить десятки раундов для MVP.
6. Если пользователь говорит «делай на своё усмотрение», заполняй некритичные параметры явно помеченными **ASSUMPTION**, не выдавай их за согласованные решения.
7. Если пользователь уже дал проектные файлы, прочитай их перед вопросами и не заставляй повторять известное.

## Этап 1. Концепт игры

Определи: игрок и фантазия роли; основное действие; зачем игрок повторяет цикл; вход → действие → результат → мотивация повторить; камера/жанр; одиночный или совместный режим; целевые устройства, если известны; визуальная идея; уникальный крючок; ограничения; как оценить «это интересно».

Проверь, что **локальная проверка core loop возможна без лобби, внешней публикации, DataStore, монетизации и сложной графики**, если они не являются самой проверяемой гипотезой.

Создай или аккуратно обнови docs/project-concept.md по references/document-contract.md.

## Этап 2. Feature Index

Создай docs/feature-index.md. Для каждой фичи: стабильный ID (F-001...), короткое имя, игровой результат, приоритет **MVP / P1 / P2**, зависимость, статус **idea / specified / implementing / tested**, ссылка на spec и проверку. Не меняй ID при перестановке пунктов.

Выбери MVP на **один завершённый, играбельный core loop**. Избегай «построить всю игру сразу». Укажи явный список **НЕ делаем в MVP**. Если локальный multiplayer не нужен для гипотезы, оставь совместный режим для P1.

## Этап 3. Интервью по центральной фиче

Применяй принципы исходного gd-doc-kickoff для одной **выбранной** ключевой MVP-фичи:
- намерение игрока → стартовые условия → действия → результат;
- правило успеха/неудачи, отмена, повторное использование, негативные сценарии;
- предметы/сущности и зависимости;
- UI/звуковой/визуальный отклик, достаточный для понимания;
- параметры и формулы, если они реально влияют на механику;
- измеримые критерии приёмки.
Если установлены references/upstream/question-bank-ru.md, references/upstream/context-triggers.md и references/upstream/gdd-core-template.md, используй их как **банк вариантов**, а не как обязательные десятки вопросов. Для Roblox-специфики не навязывай DataStore, геймпассы, аналитику, локализацию или антиэксплойт, если они не нужны для MVP; зафиксируй их как дальнейшие риски.

Сохрани docs/features/F-001_core-loop_gd-spec.md (или путь принятого ID/названия). Не добавляй в GDD архитектуру классов, конкретные API или исходники.

## Этап 4. Контракт передачи разработчику

Создай docs/mvp-handoff.md:
- активный ID и ссылка на GD spec;
- тестируемая гипотеза **одним предложением**;
- короткая последовательность из 3–6 действий игрока;
- включено/исключено из MVP;
- от 3 до 7 критериев приёмки с проверяемым исходом;
- обязательные базовые placeholder-объекты сцены (можно Parts);
- что пока неизвестно, что блокирует реализацию и что безопасно считать предположением;
- режим теста: **локальный Roblox Studio Play без публичной публикации** по умолчанию;
- признак готовности: ready-for-build или decision-needed.

Если core loop не имеет проверяемого исхода, явно отметь decision-needed. Не маскируй это под готовность.

## Выход и переход

Верни кратко: что записано, какие файлы, сколько MVP-фич, 1–2 существенных риска, статус передачи. Если в текущем запросе прозвучало «делай прототип», предложи или сразу выполни переход к $roblox-mvp-builder, если он доступен. Но **не заявляй**, что второй скилл уже отработал, до фактического запуска и проверки.

Документы — источник истины для последующего разработчика; этот скилл не должен подменять его работу.
